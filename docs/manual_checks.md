# 수동 확인 절차 (모의투자)

자동 테스트로 확인할 수 없는 것들을 **사용자가 직접** 확인하는 절차입니다.
모의투자(`IS_MOCK_TRADING=true`)에서만 하세요. 실전에서는 하지 마세요.

- 봇이 만든 주문·포지션이 KIS 앱의 실제 내역과 일치하는가
- 신 TR_ID와 지정가 주문(`00`)을 모의 서버가 받는가 (실전 전환 전 필수, 5절)

미체결 주문 취소는 국내 `cancel_order` 가 구현되지 않아 지금은 확인할 수 없습니다(3절).

## 0. 준비

```bash
.venv/bin/python -c "import config; print('IS_MOCK', config.IS_MOCK, '| CAPITAL_CAP_KRW', config.CAPITAL_CAP_KRW, '| IS_OVERSEAS_ENABLED', config.IS_OVERSEAS_ENABLED)"
```

`IS_MOCK True` 가 아니면 **여기서 멈추고** `IS_MOCK_TRADING=true` 로 고치세요. 기대 출력은 `IS_MOCK True | CAPITAL_CAP_KRW 200000.0 | IS_OVERSEAS_ENABLED False` 입니다.

`logs/bot.log` 는 실행할 때마다 이어 붙여 쓰므로 이전 실행의 줄이 남아 있습니다. 모드 줄은 봇을 시작한 **뒤에** 마지막 줄만 보세요.

```bash
grep "🔒 현재 모드" logs/bot.log | tail -1
```

`data/bot.db` 는 봇을 처음 실행할 때 만들어집니다. 이미 있다면 확인 전에 백업해 두세요.
백업은 문제가 생겼을 때 분석하려고 보관하는 것입니다. 되돌리는 데 쓰지 마세요(6절).

```bash
[ -f data/bot.db ] && cp data/bot.db data/bot.db.bak.$(date +%Y%m%d%H%M%S)
```

## 1. 매수 체결 후: 체결 조회 결과 ↔ KIS 앱 주문 내역 일치 확인

**전제**: 모의 서버로 주문이 한 건 이상 나간 뒤에 합니다. 진입 신호가 나야 주문이 생기므로 첫 실행만으로는 주문이 없을 수 있습니다.
주문번호(`broker_order_no`)는 주문 응답에서 받아 `orders` 행에 저장됩니다(T04b부터). 비어 있으면 체결 조회가 그 주문을 확정하지 못합니다.

1. 봇을 실행해 매수 주문이 나가게 합니다.
2. 로그에서 주문을 찾습니다.
   ```bash
   grep -E "주문기록|매수 주문 접수|체결" logs/bot.log | tail -20
   ```
3. DB 의 주문 기록과 KIS 앱(주문 내역)을 나란히 놓고 비교합니다.
   `raw_request` 열에는 계좌 구분 값이 들어 있으니 출력하거나 붙여 넣지 마세요.
   ```bash
   .venv/bin/python -c "
   import db
   c = db.open_db()
   for o in db.list_orders(c, limit=5):
       print(o['id'], o['symbol'], o['side'], o['qty'], o['price'], o['status'],
             o['filled_qty'], o['avg_fill_price'], o['broker_order_no'])
   c.close()"
   ```
   확인 항목:
   - [ ] 주문 수량·가격이 KIS 앱과 같다
   - [ ] `status` 가 실제 상태(접수/체결/취소)와 맞다
   - [ ] `filled_qty` 가 KIS 앱의 체결 수량과 같다 (부분 체결이면 그 수량)
   - [ ] `avg_fill_price` 가 KIS 앱의 평균 체결 단가와 같다

4. **불일치를 찾으면** 보고하세요. 체결가·수량이 다르면 응답 필드 매핑이 틀린 것입니다.

## 2. `get_all_holdings()` 응답 ↔ 실제 보유 일치 확인

대조(`reconcile`)의 정확도가 여기에 달려 있습니다. 이게 틀리면 봇이 외부 보유로 오판합니다.
봇은 장 외 시간에도 매 사이클 시작 때 대조를 돌립니다(`main.py` 의 `job()`). 이 확인은 장 외에도 할 수 있습니다.

```bash
# 국내
.venv/bin/python -c "import kis_domestic as kd; print(kd.get_all_holdings())"
# 해외
.venv/bin/python -c "import kis_overseas as kis; print(kis.get_all_holdings())"
```

KIS 앱의 보유 종목 화면과 비교하세요.

- [ ] 종목코드가 같다 (`symbol`)
- [ ] 수량이 같다 (`qty`)
- [ ] 평균 단가가 같다 (`avg_price`)
- [ ] **보유가 아닌 종목이 섞여 있지 않다** (수량 0 행이 들어오면 대조가 깨집니다)
- [ ] 보유 종목이 하나도 없으면 빈 리스트(`[]`)가 나온다

`reconcile` 이 매 사이클 도는데, 이 응답이 틀리면 대조 불일치로 중단(STATE) 🚨 로그가 반복됩니다.
그 로그가 보이면 **봇을 멈추고** 위 두 응답을 먼저 확인하세요(README 의 "매매 중단과 재개" 절).

## 3. 미체결 주문 취소 — 지금은 실행하지 마세요

국내 `cancel_order` 가 구현되지 않았습니다. 취소(02) 요청의 `ORD_QTY`·`ORD_UNPR` 값 규칙과 ETF 호가 단위표가
`docs/kis_api_fields.md` 에 없어서 추측하지 않았습니다. 호가 단위표(`_TICK_TABLE`)도 검증되지 않아
`ORDER_PRICE_TICKS` 는 `0` 으로 둡니다(코드가 음수를 0 으로 처리합니다).
`ORDER_PRICE_TICKS` 를 바꾸거나 `ORDER_TIMEOUT_MINUTES` 를 줄여 미체결을 만드는 예전 절차는 쓰지 않습니다.

미체결 주문이 `ORDER_TIMEOUT_MINUTES`(기본 30분)를 넘기면 현재 구현은 다음과 같이 동작합니다.
코드를 읽어 확인한 것이며 모의 서버에서 실행해 보지는 못했습니다.

- `<시장> <종목> 미체결 주문 #N (…주) 취소 불가 — <사유>` CRITICAL 로그가 남습니다.
- 그 주문이 UNKNOWN 으로 남아 같은 종목의 신규 매수가 막힙니다. 손절 매도는 계속 나갑니다.
- 사람이 KIS 앱에서 직접 취소하고 주문 상태를 확인해야 합니다.
- 이 상태가 `UNKNOWN_TIMEOUT_MINUTES`(기본 120분)를 넘기면 신규 매수 중단(RISK)이 걸릴 수 있습니다(추정 — 시한 판정 코드를 전부 읽지는 않았습니다).

취소가 구현된 뒤에 확인할 항목입니다(그때 이 절을 다시 씁니다).

- [ ] 취소가 실제로 일어났다
- [ ] DB 주문 상태가 `CANCELED` 다
- [ ] 부분 체결분은 취소되지 않고 포지션에 남아 있다

## 4. 타임아웃 시 재시도하지 않는지 확인 — 수동 재현 불가

네트워크를 끊는 예전 절차(Wi-Fi 끄기)로는 UNKNOWN 주문을 만들 수 없습니다. `main.py` 의 `job()` 은 사이클 시작 때 브로커 대조를 먼저 돌리고,
대조가 실패하면 주문 단계에 가지 않고 그 사이클을 끝냅니다. 네트워크를 끊으면 대조에서 먼저 실패합니다.
대조가 끝난 뒤 주문을 보내는 사이에만 끊기면 UNKNOWN 이 생길 수 있지만, 타이밍에 달려 있어 재현할 수 없습니다.

주문 결과 미확정(UNKNOWN) 경로(재시도하지 않음, 같은 종목 신규 주문 차단)는 자동 테스트와 코드 읽기로만 확인한 상태이고,
실제 모의 서버에서는 한 번도 관찰하지 못했습니다. 우연히 UNKNOWN 이 생기면 아래를 확인하고 기록하세요.

```bash
grep -E "결과 미확정|재시도하지 않습니다|UNKNOWN" logs/bot.log
```

- [ ] 주문이 한 번만 나갔다 (KIS 앱 주문 내역에 같은 주문이 2건 이상 없다)
- [ ] DB 에 `UNKNOWN` 상태 주문이 있다
- [ ] 그 다음 사이클에서 같은 종목 신규 주문이 나가지 않았다 (KIS 앱과 DB 주문 행으로 확인)

## 5. 신 TR_ID·지정가 주문을 모의 서버가 받는지 확인 (실전 전환 전 필수)

근거는 `docs/kis_api_fields.md` 에 적힌 값뿐입니다. 문서는 구 TR_ID 를 "사전 고지 없이 막힐 수 있음"이라고 명시합니다.
코드의 상수(`kis_domestic.py`)가 아래 문서 값과 같은 것은 코드를 읽어 확인했습니다. 모의 서버가 받는지는 아직 확인하지 못했습니다.

| 용도 | 문서의 모의 TR_ID | 코드 상수 |
|---|---|---|
| 주식주문 매수 | `VTTC0012U` | `_TR_BUY` |
| 주식주문 매도 | `VTTC0011U` | `_TR_SELL` |
| 주문체결조회(3개월 이내) | `VTTC0081R` | `_TR_CCLD` |
| 정정취소 | `VTTC0013U` | `_TR_RVSECNCL` (취소 미구현) |

주문구분(`ORD_DVSN`)은 문서에서 `00` 이 지정가, `01` 이 시장가입니다. 이 봇의 주문은 지정가(`00`)여야 합니다.
잔고조회(`_TR_BALANCE`)와 매수가능조회(`_TR_PSBL_ORDER`)의 TR_ID 는 `kis_api_fields.md` 에 없습니다(문서 근거 없음). 2절 확인이 그 첫 증거입니다.
모의 서버의 체결 정책(즉시 체결 여부, 시간 제한)도 문서에 없으니 관찰한 대로 기록하세요.

**주문을 강제로 내는 방법은 없습니다.** `quick_test` 에도 주문 호출이 없습니다. 진입 신호가 나서 모의 주문이 나갔을 때만 확인할 수 있고,
신호가 나지 않으면 이 확인은 미완료로 둡니다. 확인되기 전에는 실전 전환을 하지 않습니다.

1. `date` 로 평일 정규장 시간인지 확인하고, 0절로 모의 모드를 확인합니다.
2. 모의 주문이 나간 뒤 1절의 DB 조회 명령으로 주문 행을 봅니다.
3. 거절됐다면 로그에서 찾습니다. 같은 시각의 KIS 응답 줄도 함께 보세요.
   ```bash
   grep -nE "주문 #[0-9]+ 실패" logs/bot.log | tail -5
   ```
4. KIS 모의 앱의 주문 내역과 비교합니다.

- [ ] 모의 서버가 주문을 접수했다 (`broker_order_no` 가 채워졌다)
- [ ] KIS 앱에 **지정가** 주문으로 보인다
- [ ] 가격·수량이 DB 주문 행과 같다
- [ ] 거절 응답이 없다 (있으면 응답 코드와 메시지를 기록한다)
- [ ] 매도 주문도 같은 방식으로 확인했다 (청산 신호가 났을 때 별도로 확인)

거절되거나 어긋나면 TR_ID·구분 코드를 추측으로 바꾸지 말고, `docs/kis_api_fields.md` 와 대조한 뒤 보고하세요.

## 6. 확인 후 정리

`data/bot.db.bak.<타임스탬프>` 백업은 분석용 보관입니다. `data/bot.db` 를 이것으로 되돌리지 마세요.
DB 를 과거 상태로 되돌리면 KIS 의 실제 주문·보유와 어긋나 대조 불일치로 전체 중단(STATE)이 걸릴 수 있습니다(설계에서 나온 추론이며 실행해 보지는 않았습니다).

중단 플래그가 섰으면 README 의 "매매 중단과 재개 (T03·T09a)" 절을 따르세요.
상태는 `python -m risk status` 로 보고, 해제는 `python -m risk resume --reason "확인한 내용"` 으로만 합니다.
